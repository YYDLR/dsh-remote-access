# 用多轮盲测把技术文档改到「零提问可复现」

> 一份操作指南。适用于**任何要交给别人照着做的技术文档** —— 部署手册、复现指南、操作手册。
> 本文的方法和数字都来自一个真实项目：把一份 1,700 行的《手机远程连接电脑 DSH 复现指南》
> 从"自己觉得讲清楚了"改到"陌生读者能零提问做出来"，历时六轮盲测。

---

## ⚠️ 先说清楚：这是**没办法的办法**

**多轮盲测的本质，是让审阅者在脑子里把文档走一遍。** 它只能发现**逻辑与表述**层面的问题 ——
**环境层面的问题它看不见**（它没法真的去跑）。

**所以正确的优先级是**：

```
① 有干净环境（另一台机器 / 虚拟机 / 容器）→ 照着文档从零做一遍   ← 最准，能发现一切
② 只有在没法实操时 → 才用多轮盲测补位                          ← 替代方案，不是升级版
```

**真实对照（来自同一个项目）**：

| 问题 | 盲测能发现？ | 实操能发现？ |
|---|---|---|
| 命令写错 / 占位符没法确定 | ✅ | ✅ |
| 步骤顺序不对 / 缺前置条件 | ✅ | ✅ |
| 文档里嵌的源码复制进去**语法就错** | ✅ | ✅ |
| **"某个功能在我的环境里其实被拒绝了"** | ❌ 它只能看文档 | ✅ |
| **"杀毒软件会静默删掉我的脚本"** | ❌ | ✅ |
| **"推送代码还需要认证和代理"** | ❌ | ✅ |

> 那个项目里：**六轮盲测抓到的全是文本/逻辑问题**；
> 而"手机端加载某功能失败""杀软删脚本""push 要认证"——**全都是实操跑出来的**。

**结论：盲测是"手上没有第二台机器时的替代方案"，不是"更高级的方法"。**

---

## 一、为什么需要这个

**作者永远写不出自己看不懂的文档。**

你知道太多：你知道那个路径"大概是这个"、你知道那个报错"一般是那个原因"、
你知道第 5 步和第 9 步是关联的。**这些默认共识，读者一个都没有。**

于是必然发生：

- 命令能复制，但**占位符不知道换成什么**
- 步骤做完了，但**不知道算不算成功**
- 报错了，但**现象和文档写的任何一条都对不上**
- 最糟的：**你以为成功了，其实没有**（而且文档把它判为"健康"）

**盲测就是雇一个"零共识的读者"来跑一遍。**

---

## 二、核心思路：一次只解决一类问题

| 做法 | 结果 |
|---|---|
| 自己反复读、反复改 | ❌ 永远在补自己看得见的地方 |
| 一次让审阅者列 50 条 | ❌ 改不完，且改的过程会引入新问题 |
| **每轮盲测 → 逐条验证 → 按配对关系修** | ✅ 每轮收敛一点，且在收敛 |

**关键认知**：改文档**一定会引入新问题**（实测：每轮 2~5 条）。
所以目标不是"一次改对"，而是**让"我引入的问题"逐渐成为唯一的 P0 来源** —— 那说明文档本身过关了。

---

## 三、操作流程（五步）

### 第 1 步 · 把文档交给一个"零共识、只读、不许动手"的审阅者

**三个必须**：
- **零共识**：不能给它看项目的任何其他资料（交接文档、历史报告、笔记）—— 那会剧透
- **只读**：明确禁止执行任何命令（它一旦真跑，可能破坏你的生产环境）
- **不能问你**：要模拟"读者孤立无援"的状态

提示词模板见第五节，直接复制。

### 第 2 步 · 拿回报告，**逐条上机验证**

**报告不是圣旨。** 实测驳回率约 1/6，而且驳回的理由往往是**它的改法本身是错的**。

每一条判成三档：

| 判定 | 含义 |
|---|---|
| **成立** | 问题真实存在 → 采纳（或采纳改写后的方案） |
| **不成立** | 前提就不成立 → **驳回，并写下实测证据** |
| **改法不可用** | 问题成立，但它给的修法行不通 → **换一个改法** |

**必须亲自验的理由**：审阅者只能"在脑子里跑"，它对现实的假设可能错。
例：它建议"自动去找 `session.lock` 文件"，而那个文件在 Windows 上**根本不存在**（锁是内核对象）。

### 第 3 步 · 修 —— **但先做配对检查**

见第六节「三条自查法」。**不做这一步，你就是在制造下一轮的 P0。**

### 第 4 步 · 按**错误类型**全文扫一遍（不是按改动清单）

这是最容易被跳过、也最有效的一步。见第六节。

### 第 5 步 · 再盲测

**最好换一个审阅者**（不同模型/不同会话），避免它被你上一轮的结论影响。

---

## 四、怎么判断"可以停了"

**停止条件**：

> 当新一轮的 P0 **全部来自"我自己的编辑手误"**（而不是"读者做不出来"）时 —— **停**。

理由：那说明文档的**内容**已经没有问题了，剩下的只是在追自己的尾巴。

**实测数据**（六轮）：

| 轮次 | P0 | 其中来自作者自己的手误 |
|---|---|---|
| 第三轮 | 7 | 5 |
| 第四轮 | 5 | 3 |
| 第五轮 | 4 | 2 |
| 第六轮 | 3 | **2**（且全是手误，无内容问题）|

P0 在减少、性质在变轻 → **可以停了**。

## 五、审阅提示词模板（直接复制）

```markdown
# 任务：只读审阅一份技术文档（**禁止执行任何命令**）

你是一个**从未见过这个项目**的 AI。下面是一份完整的《XXX 部署指南》。
它的目标是：让读者照着它，从零把 XXX 搭起来。

## 硬性约束（请严格遵守）

1. **绝对不要执行任何命令** —— 不要跑 `xxx` / `yyy` / `curl` / `powershell`，
   不要创建或修改任何文件、计划任务、服务、注册表项。**这是别人的生产环境，跑一次就可能被破坏。**
2. 不要联网搜索、不要下载任何东西。
3. 你的全部工作就是**在脑子里把这份文档走一遍**。
4. 如果某一步"不实际跑一下就没法确认"，**就把它列进报告并说明这一点**，**不要真的去跑**。

## 你要模拟的场景

想象你手边只有：<列出读者会有的东西，例如一台干净的 Windows 电脑 + 浏览器 + 一个账号>。
**除此之外什么都没有** —— 没有历史、没有作者的机器、也没有作者可以随时问。

逐节往下走，每一步问自己三个问题：
- **我能照着做出来吗？**（命令能直接复制吗？占位符我知道换成什么吗？）
- **做完这步，我怎么知道成功了？**（有可观察判据，还是只能靠猜？）
- **如果这步失败了，我知道为什么吗？**

## 请特别检查

- 所有 `<占位符>` 是不是都能**唯一确定**地替换？
- 命令能不能**原样复制**就跑？（注意不同 shell 的差异、引号嵌套、转义字符）
- 前面章节的假设，后面章节有没有兑现？有没有"用到前面从没说过的东西"？
- 有没有哪一步**只说做什么、没说怎么验证**？
- 有没有哪一步需要读者提供只有他自己知道的信息，而文档没说去哪拿？
- 有没有任何一处**会覆盖或破坏读者已经存在的东西**？**逐条列出，并说明"重复执行会怎样"。**
- **有没有哪一处"失败"会被文档自己的判据误认为"成功"？**（这是最危险的一类）

## 输出格式

**先说一句话结论**：照着它，一个不知情的人能不能零提问做出来？

然后一张分级清单，每条含「**位置 → 现状 → 问题 → 建议改法**」，改法尽量写成可直接粘贴的内容：

| 级别 | 含义 |
|---|---|
| **P0** | 不改会导致步骤失败、或让人得出错误结论、或造成数据风险 |
| **P1** | 大概率踩坑、排障困难、安全说明缺失 |
| **P2** | 完善性修订 |

最后两节：【最容易卡住的 3 个地方】【文档写得好的地方】

**再说一次：只读。不要执行任何命令，不要修改任何文件。**

下面是文档全文：
```

## 六、三条自查法（**这一步比盲测更重要**）

### ① 配对自查法 —— "改了 A，别忘了和 A 配对的 B"

改任何一处之前，先问：**它的配对项在哪？**

| 你改的是 | 必须同步检查 |
|---|---|
| **装 / 建**某样东西 | **卸 / 删**的那一节 |
| **写**一个文件 | **读**它的地方（路径、文件名一致吗） |
| **加**一条命令 | 它依赖的**前置条件**（目录在不在、变量设了没） |
| **改**源码 / 脚本 | 文档里**引用它的样例输出**（版本号、日志行、字段名） |
| **替换**一段说明 | **删掉**旧的那段 |
| **正**向流程 | **反**向流程（启用↔停用、部署↔回滚、加↔减） |
| **改动了"系统"** | 在纸上**数一遍**：卸载 / 还原章节必须**一一对应** |

### ② 文档内嵌源码 → **必须 diff**

**光看是看不出来的。**

```bash
# 从文档里提取源码块，和实际文件逐字节比对
node -e "
const fs=require('fs');
const L=fs.readFileSync('文档.md','utf8').split('\n');
const s=L.findIndex(l=>l.includes('<源码块第一行的特征串>'));
let e=-1; for(let i=s+1;i<L.length;i++){ if(L[i].trim()==='\`\`\`'){e=i;break;} }
fs.writeFileSync('/tmp/from-doc.txt', L.slice(s,e).join('\n')+'\n');
"
diff /tmp/from-doc.txt 实际文件 && echo "✅ 一致"
```

真实案例：文档里的源码块中，`Write-Log '=== xxx ==='` 的**外壳被替换掉了**，只剩一句裸文本
→ 读者整段复制 → **语法错误，脚本根本起不来**。而文档还把这行当作"验证判据"。
**靠眼睛读一百遍也发现不了，diff 一秒就抓到。**

### ③ 按**错误类型**全文扫（不是按改动清单）

自查"我改了哪几处"永远会漏掉"**同一类错误还出现在别处**"。

**做法**：列出这类错误的**特征**，然后全文 grep。

| 错误类型 | 怎么扫 |
|---|---|
| "重启服务"的命令无效 | grep 所有 `restart` / `run` 的用法，逐个确认前提成立 |
| 备份 / 留档 | grep 所有备份路径，确认目录**先建了** |
| 删除清单不全 | 对照"新产生的文件"，确认都进了删除清单 |
| 行尾注释 | grep 行尾注释符（**CMD 里行尾的 `::` 不是注释**）|
| 悬空引用 | grep "见第 N 节"，逐个确认那一节真的有 |

实测效果：一次扫出 **4 处**，其中 2 处是上一轮报告**提过、我漏修的**。

## 七、反面教训（都真实发生过）

1. **别相信"我检查过了"** —— 连续两轮我都在自认为检查过之后，又引入了新 P0。
2. **别照抄审阅者的改法** —— 它只动脑不动手，对现实的假设可能是错的。
3. **别一次改太多** —— 改动越大，配对项越多，漏的概率越高。
4. **别把"失败"写成"健康"** —— 这是所有问题里最危险的一类：
   文档说"看到 `standby` 就是正常待命"，而某种情况下 `standby` 恰恰意味着"锁永远不会被释放"。
   **看到"某种状态被判定为正常"时，多问一句：它有没有可能其实意味着失败？**
5. **改动必须有"连带清单"** —— 尤其是"系统级改动"（电源、服务、注册表、配置文件、自动登录），
   改了几处，卸载节就得有几处还原，一个都不能少。

## 八、证据过审（拿到证据之后，先审方法）

**"拿不出证据别下结论"只说对了一半。** 另一半是：

> **拿到证据之后，也要先检查方法本身 —— 要自审，要对自己的结论负责。**

**为什么必要（真实翻车）**：查"压缩摘要里有没有重复段落"时，提取函数把**同一份正文抓了两遍**再拼接，
于是得出"**113 段里 56 个重复**"这个**看起来很成立**的结论。

- **破绽**：比例太整齐了（正好一半）——**"可疑的整齐"本身就是线索**
- **改正**：改成只看"最长的那一个字符串"后重测 → **56 段，真重复 = 0**

### 下结论前，问自己这四个问题

| 问题 | 在查什么 |
|---|---|
| **数据源对不对？** | 我看的是真实文件，还是它的某个副本 / 缓存 / 旧版本？ |
| **会不会重复、截断、串字段？** | 提取逻辑有没有把同一份内容算两遍？有没有被长度限制切掉？字段取对了吗？ |
| **样本量够吗？** | 一次观察不算规律；"太整齐"的结果往往是方法有问题 |
| **别人能按我的方法复现吗？** | 我说的"判据"是可执行的吗？还是一种感觉？ |

### 交付结论时的三个要求

1. **附上怎么得出的**（命令、字段、判据）—— 让别人能复核，而不只是"相信我"
2. **区分"事实"和"推测"** —— 推测要显式标出来（如 `推测（未验证）`）
3. **错了就直接认** —— 掩饰一次，后面所有的结论都会被怀疑

> **一句话：证据也要过审。对自己的结论负责，意味着别人按你说的方法能复现出同样的结果。**

## 九、一页速查

```
① 写提示词（零共识 + 只读 + 禁止执行）
② 交给陌生读者 → 拿报告
③ 逐条验证：成立 / 不成立 / 改法不可用（别照抄）
④ 修 —— 先做配对检查
⑤ 按错误类型全文扫（grep 特征，不是看改动清单）
⑥ 若是"内嵌源码" → diff 逐字节比对
⑦ 再盲测（换审阅者）
⑧ 直到 P0 全部来自"自己的编辑手误" → 停
⑨ **拿到"证据"后，先审方法本身**（数据源 / 重复 / 样本）—— 能被别人复现才算数
```

**一句话**：盲测帮你发现"读者做不出来"的地方，**自查防止你把它们换成"自己造的新坑"**。
两者缺一不可 —— 只盲测不自查，就是原地转圈。
